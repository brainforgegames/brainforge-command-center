# Brainforge owner instructions

Recorded from the owner's direct instructions through 27 October 2026. Read this at every worker start and supervisor handoff. New explicit owner instructions take precedence. This file must be available locally; a dashboard outage must not hide these rules.

## Work order and delivery

- Quality over quantity: useful, correct implementation matters more than task counts, test counts, report volume or speed. Focused verification is required; repeated speculative verification is not progress by itself.
- Finish already-started work end to end. Queue new requests unless the owner explicitly makes them urgent. Do not interrupt implementation for each new chat message.
- Deliver meaningful features and fixes. Testing supports delivery: use focused checks appropriate to the change, then move on. Do not replace implementation with repeated broad tests, speculative edge-case work, screenshots, planning or research.
- Clearly distinguish a confirmed defect from a preventive test. Never present a test scenario as a bug found in the app.
- Keep two useful workers where safe. Use separate repositories or explicitly isolated non-conflicting work. Never create overlapping edits just to show two active workers. Serialize Unity checks.
- Use latest saved priorities; last verified allocation was Sikhi Khoj 90%, BCC 10%. Preserve parked work. If primary work cannot run, approved Drivenix implementation is allowed as fallback, then company improvement research when no approved implementation can run.
- A BCC/Firebase outage must not stop unrelated approved work. Use durable saved priorities, tasks and local ownership; save results locally and sync later. Never guess unknown ownership, discard checkpoints or overwrite newer owner decisions.
- A blocked task does not block the company. Preserve it and take the next useful approved task. Pause affected work when security, data loss or conflicting edits make continuation unsafe. Respect explicit owner stop instructions, account limits and the daily pause.
- No purchased credits or billing upgrades. Checkpoint on plan/capacity limits and retry automatically. Daily pause 23:00–00:00 IST; daily report 22:00 IST.
- Supervisor may create/review/merge validated PRs. Only the owner publishes to Play Store/App Store. Preserve dirty originals and credentials.

- Finish Hindi integration, useful visual improvements and empty/unnecessary scrolling fixes. Screenshots come after feature work, not ahead of it. Use emulator testing where feasible; avoid waiting unnecessarily for a physical phone.

Do not claim posts or posting automation exist until verified. Obtain agreed publishing scope before automated public posting.

## BCC and communication

- Dark, professional, readable design; short everyday bullets explaining what finished, what is blocked and what comes next. Technical evidence goes in optional Details.
- Finished means actually completed, not drafts, tests planned, or unavailable features. Every count must open its matching list. Include useful timestamps.
- Keep Projects, Time split, Analytics, Screenshots and Ideas in their own sections. Do not duplicate Projects on Today or show paused projects as upcoming active work. Sort by priority, paused last.
- Analytics should be uncluttered with filters, meaningful charts, time/token and completion breakdowns. Never invent usage history. Use verified completion recording for finished tasks.
- Feedback happens in chat. Ask only specific questions genuinely requiring the owner; do other eligible work meanwhile.
- Do not claim continuous/autonomous work based on instructions alone. Verify actual processes, task progress, handoffs and outage recovery. Report failures honestly.
